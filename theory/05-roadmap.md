# 05 — 实施路线图（30/60/90 天）

> 从零到建立持续对抗测试能力的渐进计划。

---

## 第一阶段：建立基础（第 1-30 天）

**目标**：完成第一次完整的对抗测试。

### 第 1-7 天：环境搭建

- [ ] 克隆本仓库，选择适配器（WorkBuddy / Cursor / Claude / Generic）
- [ ] 阅读 `theory/01-overview.md`，理解核心概念
- [ ] 阅读 `theory/02-attack-taxonomy.md`，确定你的产品适用的攻击分类
- [ ] 阅读 `tools/templates/rules-of-engagement.md`，定义测试边界

### 第 8-14 天：首次测试

- [ ] 选择 1 个核心功能模块作为试点
- [ ] 使用 Developer AI 产出对抗测试摘要（`tools/developer-ai-spec.md`）
- [ ] 使用 Adversarial AI 执行 A1-A3（边界 + 注入 + 权限）测试
- [ ] 记录首批发现，修复高优先级问题

### 第 15-21 天：扩大覆盖

- [ ] 扩展到第 2-3 个功能模块
- [ ] 完成 A4-A6（并发 + 异常 + 业务逻辑）测试
- [ ] 如果是 LLM 系统，启动 B1-B3 测试
- [ ] 建立测试基线数据

### 第 22-30 天：流程固化

- [ ] 建立测试结果归档机制
- [ ] 编写团队对抗测试操作手册
- [ ] 设置定期测试提醒（建议每发布周期一次）
- [ ] 输出第一份完整测试报告

---

## 第二阶段：深化覆盖（第 31-60 天）

**目标**：建立自动化对抗测试流水线。

- [ ] 将对抗测试集成到 CI/CD 流水线中
- [ ] 部署自动化工具（Garak、PyRIT、Promptfoo 等）
- [ ] 启用 AI-on-AI 自动化测试模式（攻击者 LLM + 裁判模型）
- [ ] 扩展到完整攻击分类（B4-B8、C、D 类）
- [ ] 跨平台适配：确保测试覆盖所有部署环境
- [ ] 建立载荷库维护机制（持续更新攻击载荷）

---

## 第三阶段：持续运营（第 61-90 天）

**目标**：形成组织级的对抗测试文化。

- [ ] 建立 Red Team 内部能力（招聘/培训对抗测试人员）
- [ ] 定期跟踪新攻击技术（订阅 CVE、安全公告）
- [ ] 差分测试：对比不同实现/版本的安全行为差异
- [ ] 每季度执行一次完整的回归对抗测试
- [ ] 建立跨团队对抗测试知识共享机制
- [ ] 贡献回社区：将新的攻击模式和修复策略提交到本仓库

---

## 成熟度模型

| 等级 | 特征 |
|------|------|
| **L1 初始** | 无系统化对抗测试，仅在安全事件后被动响应 |
| **L2 管理** | 有基本的对抗测试流程，覆盖核心模块 |
| **L3 定义** | 完整的对抗测试方法论，自动化工具辅助，定期执行 |
| **L4 量化** | 指标驱动：ASR、覆盖率、修复时间等量化跟踪 |
| **L5 优化** | 持续改进：AI-on-AI 自动化 + 跨团队协作 + 行业贡献 |

**大多数团队的目标是达到 L3-L4 即可**。L5 适用于 AI 安全团队和监管合规场景。
