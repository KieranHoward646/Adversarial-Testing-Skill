# 03 — 对抗测试方法论

## 四阶段工作流

```
Phase 1: 侦察与建模    →  Phase 2: 基线测试    →  Phase 3: 对抗攻击    →  Phase 4: 修复与报告
    (理解攻击面)              (建立正常基线)           (执行攻击载荷)            (闭环)
```

---

## Phase 1：侦察与威胁建模

### 1.1 攻击面映射

识别目标系统的所有入口点：

- [ ] API 端点（REST、GraphQL、gRPC）
- [ ] 用户输入界面（Web 表单、CLI 参数、文件上传）
- [ ] 外部集成（Webhook、第三方 API、数据库连接）
- [ ] Agent 工具（LLM Agent 可调用的所有工具）
- [ ] 检索系统（RAG 知识库、向量数据库）

### 1.2 威胁识别

| 维度 | 问题 |
|------|------|
| 攻击者动机 | 好奇/经济利益/间谍/破坏？ |
| 攻击路径 | 外部攻击/供应链/内部威胁？ |
| 攻击生命周期 | 侦察→武器化→投递→利用→安装→C2→行动 |
| 关键资产 | 用户数据/IP/模型权重/API 密钥？ |

### 1.3 情境: Rules of Engagement

在进行对抗测试前，必须明确：

- ✅ 测试范围：哪些系统、哪些端点、哪些数据
- ✅ 测试时间窗口
- ✅ 允许的操作边界（参考 `tools/templates/rules-of-engagement.md`）
- ❌ 禁止的操作：DROP/TRUNCATE/无条件 DELETE/生产数据修改/外部真实请求
- ❌ 发现严重漏洞时的停止规则

---

## Phase 2：基线测试

在发动攻击之前，先建立正常行为基线。

### 2.1 功能基线

- 验证系统在正常输入下的行为
- 记录所有端点的标准响应格式
- 确认安全机制的默认行为（认证、限流、输入校验）

### 2.2 安全基线

- 询问模型/系统"你会拒绝哪些请求？"
- 测试已知的安全策略边界
- 记录安全机制的触发阈值

---

## Phase 3：对抗攻击执行

按 `02-attack-taxonomy.md` 的分类执行。**强制顺序**：

```
1. 输入边界测试     ← 建立基本健壮性基线
2. 注入测试         ← 最高优先级安全漏洞
3. 权限与认证       ← 访问控制
4. 并发与竞态       ← 时序相关漏洞
5. 异常与资源耗尽    ← 容错能力
6. 业务逻辑         ← 领域特定缺陷
7. LLM 专项         ← (如适用) Prompt Injection / Jailbreak / Agent 攻击
8. 网络协议专项     ← (如适用) SSL/协议状态机
```

### 3.1 每类测试的执行模板

```
对于分类中的每个测试点：
1. 构造精确的测试输入
2. 发送请求/调用
3. 记录实际响应（状态码 + 响应体）
4. 对比预期行为 → PASS / FAIL / SKIP
5. 扩展：对边界值额外测试 ±1
```

### 3.2 LLM 专项：AI-on-AI 自动化测试

对于 LLM 系统，推荐使用自动化方式：

```
攻击者 LLM（给定自然语言目标）
  → 规划攻击树 → 选择技术 → 组合变换
  → 编码/翻译/角色扮演/拆分
  → 执行攻击 → 获取响应
  → 裁判模型评分 → 结构化发现
```

参考工具：Garak、PyRIT、Promptfoo Hydra

## Phase 4：修复与报告

### 4.1 修复决策树

```
FAIL 发现
├── 已知豁免（RoE 中声明）→ SKIP
├── 安全可自动修复 → 修复 → 回归测试 → 确认 PASS
└── 不安全/不确定 → 记录 → 提交人类开发者
```

### 4.2 修复原则

| 问题类型 | 修复策略 |
|---------|---------|
| 输入校验缺失 | 添加校验层（不是单点修补） |
| SQL 注入 | 参数化查询（不要自己拼接转义） |
| XSS | 输出编码（不是输入过滤） |
| 越权 | 资源所有权校验中间件 |
| 竞态条件 | 数据库行锁/分布式锁 |
| Prompt Injection | 输入清理 + 输出过滤 + 结构化提示 + 权限分离 |
| Jailbreak | RLHF / Constitutional AI / 对抗训练 |
